# DocChat

A small retrieval-augmented chatbot for question answering over documents. Documents are cleaned,
chunked, embedded with sentence-transformers and stored in ChromaDB; a Flask app streams each answer
to the browser token by token over a WebSocket and cites the page it came from. Questions the
documents can't answer get a "not found" reply instead of a guess.

Stack: Python, LangChain, ChromaDB, sentence-transformers, Flask, flask-sock (WebSocket).

## How it works

```
data/docs/*.pdf|txt
      |  pypdf                      one text blob per page
      v
cleaning.py   strip repeated headers/footers and page numbers, rejoin hyphenated
              line breaks, unwrap lines, normalise unicode
      |
      v
ingest.py     split page by page (RecursiveCharacterTextSplitter) so every chunk has exactly one
              page number -> embed (all-MiniLM-L6-v2, normalised) -> ChromaDB (cosine)
      |
question ---> retrieval.py   top-k chunks + cosine distance
                  |  best chunk farther than MAX_DISTANCE?  --> "not found"
                  v
              generate.py    stream tokens
                  |            - default: extractive, returns the best-matching sentences
                  |            - OPENAI_API_KEY set: LangChain chat model grounded in the chunks,
                  |              told to reply NOT_FOUND when the context has no answer
                  v
app.py  /ws   {"type":"token"} ... {"type":"done","sources":[{"source","page"}]}
static/       chat page that appends tokens as they arrive and shows source chips
```

## Run it

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python app.py                       # http://127.0.0.1:5050
```

The first start downloads the embedding model and indexes `data/docs/`. Drop your own `.pdf` / `.txt`
files in that folder and `POST /api/ingest` (or delete `chroma_store/`) to re-index.

Port 5050 rather than 5000 because AirPlay Receiver owns 5000 on recent macOS.

The two PDFs in `data/docs/` are **synthetic**: a made-up espresso-machine manual and a made-up
savings-account agreement, generated by `data/generate_sample_docs.py` (needs `requirements-dev.txt`).
They exist so the project runs out of the box and so the answers in the test set are known exactly.

### WebSocket protocol

Send `{"question": "..."}`. You get back a stream of JSON messages:

| message | meaning |
|---|---|
| `{"type":"token","text":"..."}` | one piece of the answer |
| `{"type":"not_found","message":"..."}` | nothing in the documents answers it |
| `{"type":"done","found":true,"sources":[{"source":"x.pdf","page":4}]}` | end of answer, with citations |
| `{"type":"error","message":"..."}` | bad payload or server error; the socket stays open |

Extractive mode has nothing to wait for, so it sleeps `EXTRACTIVE_TOKEN_DELAY` (20 ms) between words
purely so the browser visibly streams. Set it to `0` to disable.

## Tuning chunk size and top-k

`eval/questions.json` holds 35 questions whose answers are known (each labelled with the document and
page the answer is on) and 12 questions the documents can't answer. `python -m eval.run_eval` indexes the
documents at each chunk size and scores retrieval **end to end**:

- answerable question: correct if the known answer text is in the top-k chunks *and* the best chunk is
  close enough not to be refused
- unanswerable question: correct if it is refused

The "not found" threshold is tuned separately for every (chunk size, k). Overlap is fixed at 15% of the
chunk size. Overall accuracy (47 questions):

| chunk size | k=1 | k=2 | k=3 | k=4 | k=5 |
|---:|---:|---:|---:|---:|---:|
| **150** | 0.74 | **0.83** | 0.83 | 0.83 | 0.83 |
| 250 | 0.68 | 0.72 | 0.72 | 0.72 | 0.72 |
| 400 | 0.68 | 0.70 | 0.72 | 0.74 | 0.77 |
| 600 | 0.66 | 0.70 | 0.74 | 0.74 | 0.74 |
| 800 | 0.68 | 0.74 | 0.74 | 0.74 | 0.74 |
| 1200 | 0.68 | 0.72 | 0.74 | 0.77 | 0.77 |

Chosen defaults: **chunk size 150, k = 2, threshold 0.58** (best accuracy; ties go to the smallest
prompt). Full grid in `eval/results.csv`, threshold curve in `eval/threshold.csv`. At that setting:

| measure | value |
|---|---:|
| known answer present in the 2 retrieved chunks | 35/35 |
| best chunk is on the labelled page (what gets cited) | 33/35 (94%) |
| answerable questions answered (not wrongly refused) | 34/35 (97%) |
| unanswerable questions correctly refused | **5/12 (42%)** |
| overall, threshold tuned on these same questions | 83% |
| overall, each question scored with a threshold tuned on the other 46 (leave-one-out) | 79% |

### What these numbers do and don't say

- **The "not found" gate is weak for near-topic questions.** It catches clearly off-topic questions
  ("capital of France", "weather tomorrow") but not ones that sound like the document: "How do I make cold
  brew with the Aurora X200?" lands *closer* to the manual than many real questions do, so embedding
  distance can't separate them. Without an LLM, those get a nearby, wrong sentence. A cross-encoder
  relevance score separated them somewhat better in a side experiment that isn't in this repo (AUC about
  0.83-0.90 vs 0.69-0.83 for distance) but still not reliably, so it isn't included. With `OPENAI_API_KEY` set, the prompt
  tells the model to answer `NOT_FOUND` when the context lacks the answer and that reply is turned
  into the same "not found" message; I haven't measured how well a real model does that (see below).
- The question set is small (47), written by the same person who wrote the documents, and the
  thresholds are tuned on it. The leave-one-out figure is the fairer estimate; neither is a held-out test.
- All 35 answerable questions are single-fact lookups, which favours small chunks. Questions that need
  several sentences of context would likely do better with larger chunks. Set `CHUNK_SIZE` to change it.
- Distances depend on the embedding model; if you change `EMBEDDING_MODEL`, re-run the eval.

## Tests

```bash
pip install -r requirements-dev.txt
pytest
```

33 tests, against the real embedding model and a real ChromaDB index (no mocks for retrieval): cleaning
rules, page metadata on every chunk, that each labelled answer really is on its labelled page,
retrieval hits the right page, off-topic questions are refused, extractive and LLM streaming, and a
live WebSocket round-trip against a running Flask server.

## Not verified

- **Answer generation with a real LLM.** No API key was available. The `LLMGenerator` path is tested
  with LangChain's fake chat model (streaming in pieces, `NOT_FOUND` handling, page labels in the prompt),
  not with OpenAI. Answer quality, latency and abstention behaviour of a real model are unmeasured.
- Anything beyond the two sample PDFs: no scanned/OCR PDFs, tables, or large corpora.
- The Flask development server is used; it is not a production deployment.
